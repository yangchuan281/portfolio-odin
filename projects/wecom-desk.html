01 context

Five questions a week, and no record of any of them.

IT requests came in as DMs to whoever was on duty. No queue, no record, no way to tell whether the answer actually solved anything — and the same five questions every week.

The shape I wanted was the boring one IT departments already use: an answer first, a person when the answer is not good enough, and a ticket that exists whether or not the conversation went well.

02 design

The hand-off is the interesting edge.

One MySQL instance plus cron retries instead of a message broker. The risk I actually feared was duplicates, so the ITSM adapter carries an idempotency key: a retry cannot open a second ticket.

03 what broke

The first version logged what people typed.

Early sessions wrote whatever the user typed straight into the message table — including passwords and phone numbers. Message bodies are now masked before they persist, and every state transition (hand-off, pickup, transfer, close, rating) writes an operation_log row.

That was the point where "it works" stopped being enough: a service desk holds the same secrets as the systems it supports, so the table became the place to fix it, not the chat window.

Scope boundaries — what it does not do

  • One MySQL instance, no broker: if the queue table is unreachable, hand-offs queue up rather than fail over.
  • The knowledge base answers from configured entries; it is not a general-purpose model that reads your wiki.
  • The ITSM adapter speaks one endpoint shape. A different vendor needs its own adapter, not a config change.
  • Verified in a WeCom test enterprise, not in production traffic.
